\section*{Points 1 and 11: Open-set Clarification and Threshold-Based Operating Points}

\paragraph{Reviewer request (Point 1).}
\emph{True open-set verification experiment with non-enrolled identities. Your current leave-one-dataset-out protocol evaluates unseen test identities, but all probe identities appear to come from the enrolled test population. Reviewer 2 and Reviewer 3 are effectively asking for a stricter protocol where some probe subjects are not enrolled at all and must be rejected using a fixed threshold.}

\paragraph{Reviewer request (Point 11).}
\emph{Threshold-based operating-point evaluation. Reviewer 2 asked for false acceptance at specific false rejection operating points. Since the manuscript currently reports mainly AUC and EER, add thresholded operating points. Report TAR @ FAR=1\%, TAR @ FAR=0.1\% if stable, FRR/FMR under a fixed threshold, and unknown acceptance rate for non-enrolled probes.}

\paragraph{Response.}
We agree that the manuscript should distinguish two related but different notions of open-set evaluation. The current leave-one-dataset-out protocol is already \emph{subject-disjoint open-set} with respect to training identities: the test set belongs to the held-out dataset, and none of its identities are seen during training. The stricter \emph{enrollment-based unknown-rejection} setting requested by the reviewers is a stronger gallery/probe protocol and should be described separately from the existing cross-dataset subject-disjoint evaluation.

To directly address the reviewer concern on thresholded operating points, we now report threshold-dependent verification metrics derived from the saved FAR/FRR curves, namely TAR at FAR$=0.1\%$, FAR$=1\%$, and FAR$=10\%$, in addition to AUC and EER. We provide these results for both the half-subject and full-subject settings, now including the completed VeinAttNet runs.

\paragraph{Additional clarification: per-identity training/validation image split.}

Reviewer~2 also noted that the manuscript states that the number of samples per identity is 
deliberately varied between the training and validation partitions, but the exact split policy was 
not given clearly. 

In the implemented leave-one-dataset-out protocol, source-dataset identities are partitioned at the 
image level before training. Because FV-300 contains far more images per identity than the other 
datasets, we use a $7{:}3$ train/validation split for FV-300. For MMCBNU, FV-USM, PolyU, and VERA, 
we use a $1{:}1$ split. The effective per-identity counts are summarised below.

\section*{Point 3: Loss Comparison Against Strong Angular-Margin Baselines}

\paragraph{Reviewer request (Point 3).}
\emph{Loss comparison against strong angular-margin baselines. Your current loss discussion introduces the Centroid Angular Hybrid Loss, but the reviewers want direct comparison against ArcFace / CosFace / SphereFace-type strong baselines, not just weaker alternatives. This comparison is essential.}

\paragraph{Response.}
We agree that stronger angular-margin losses should be included explicitly. Using the same $ABDE \rightarrow C$ protocol (FV-USM as the held-out dataset), we evaluated ArcFace, MagFace, and AdaFace. \section*{Point 4: Beta Sensitivity for the Proposed Loss}

\paragraph{Reviewer request (Point 4).}
\emph{Beta sensitivity study for the proposed loss. Reviewer 2 explicitly asked for the effect of the balancing parameter $\beta$. Since $\beta$ appears in the loss formulation, this is a direct missing experiment.}

\paragraph{Response.}
We agree that the sensitivity of the balancing parameter $\beta$ should be made explicit. We therefore ran a focused ablation on the same $ABDE \rightarrow C$ protocol used for the other loss studies, varying the contribution of the angular component while keeping the rest of the training setup fixed. The results are reported below. For reference, the default setting used in the main model is $\beta = 0.3$.

\begin{table}[ht!]
    \centering
    \begin{tabular}{|c|c|}
        \hline
        $\beta$ & EER (\%) \\
        \hline
        0.1 & 9.07 \\
        0.3 (default) & \textbf{7.44} \\
        0.5 & 10.60 \\
        0.9 & 11.57 \\
        \hline
    \end{tabular}
    \caption{Sensitivity of the proposed loss to the balancing factor $\beta$ on the $ABDE \rightarrow C$ protocol. Lower EER is better.}
    \label{tab:rebuttal_beta_ablation}

This trend is consistent with the intended role of $\beta$: when the angular term is weighted too weakly, the loss does not fully exploit the added angular supervision, and when it is weighted too strongly, optimisation becomes less stable and verification performance degrades. The intermediate default setting $\beta = 0.3$ gives the best result among the tested values, which supports the choice used in the main experiments.

\section*{Points 8 and 9: BCDE$\rightarrow$A Anomaly and VERA Performance Drop}

\paragraph{Reviewer request (Point 8).}
\emph{Analysis of the BCDE$\rightarrow$A anomaly where handcrafted methods beat many deep models. Table 5 in the manuscript shows MCP / RLT / WLD doing unexpectedly well on some cases, while the text says the proposed method consistently outperforms handcrafted and deep methods. \paragraph{Reviewer request (Point 9).}
\emph{Analysis of the VERA performance drop. Reviewer 2 asked for discussion of why the VERA case is much weaker. The paper itself notes that VERA is the most difficult and lowest-quality dataset.}

\paragraph{Response.}
To address both points, we analysed dataset quality using the handcrafted quality measures implemented in \texttt{vein\_quality\_assessment.py}. The intent of these measures is not to claim a calibrated universal quality scale, but to provide consistent descriptive evidence about sharpness, structure continuity, and local contrast across the datasets used in our experiments.

For a grayscale image $I$ over pixel domain $\Omega$, the four measures used in the rebuttal are:
\begin{align}
Q_{\text{grad}}(I) &= \frac{1}{|\Omega|}\sum_{p \in \Omega} \sqrt{G_x(p)^2 + G_y(p)^2}, \\
Q_{\text{coh}}(I) &= \frac{1}{B}\sum_{b=1}^{B}
\left(
\frac{\sqrt{(j_{11}^{(b)}-j_{22}^{(b)})^2 + 4(j_{12}^{(b)})^2}}
{j_{11}^{(b)} + j_{22}^{(b)} + \varepsilon}
\right)^2, \\
Q_{\text{lap}}(I) &= \mathrm{Var}(\Delta I), \\
Q_{\text{con}}(I) &= \frac{1}{B}\sum_{b=1}^{B} \sigma_b,
\end{align}
where $G_x$ and $G_y$ are Sobel derivatives, $(j_{11}^{(b)},j_{22}^{(b)},j_{12}^{(b)})$ are block-wise structure-tensor moments, $\Delta I$ is the Laplacian response, and $\sigma_b$ is the standard deviation inside block $b$. In all four cases, larger values indicate better local structure visibility or contrast.

This table helps explain both reviewer concerns. First, the $BCDE \rightarrow A$ split corresponds to FV-300, which is a relatively clean and well-controlled dataset and also has far more images per identity than the other datasets. In such a setting, handcrafted vessel-enhancement and template-matching methods remain very competitive, because the vein patterns are already sharp and high-contrast. Therefore, the observation that MCP/WLD can outperform several deep baselines on this split is not inconsistent with the rest of the cross-dataset story; rather, it means that the manuscript should use the more precise claim of \emph{strong overall generalisation} instead of implying dominance over every handcrafted baseline on every split.

Second, the VERA drop is consistent with both the dataset composition and the quality analysis. VERA has the lowest gradient-coherence score among all datasets and only two images per subject, which means each identity is substantially under-represented. This combination makes $ABCD \rightarrow E$ the most difficult setting: image quality is weaker, the open-sensor acquisition is more variable, and the per-subject evidence is minimal. Therefore, the reduced performance on VERA is expected and does not indicate a protocol inconsistency; instead, it reflects a genuine low-quality, low-sample, high-shift test condition.

\section*{Implementation Details and Latency}

\paragraph{Architecture and loss.}
The proposed \textit{OpenVeinNet} is implemented in PyTorch (\texttt{v2.8.0+cu128}). Input finger-vein ROIs are read as grayscale images, scaled to $[0,1]$, replicated to three channels, and resized to $224\times224$. In the leave-one-dataset-out setting, the training set is formed by pooling identities from the four non-held-out datasets, while the held-out dataset is used only for evaluation. The encoder consists of a three-block DSConv stem with kernel sizes $\{9,7,3\}$ and stride $2$, giving a channel progression of $16 \rightarrow 32 \rightarrow 64$, followed by a learnable positional embedding of size $1 \times 64 \times 28 \times 28$. The backbone then applies two Grapher stages with $4$ and $6$ internal Grapher units, hidden/output dimensions $(256,128)$ and $(512,256)$, and graph kernel size $9$, followed by adaptive average pooling to produce a $256$-dimensional embedding. During training, this embedding is supervised by the proposed Centroid Angular Hybrid (CAH) loss, which combines a standard classifier cross-entropy term with a $\beta$-weighted angular cross-entropy term computed against a learned centroid matrix; the default setting used throughout the main experiments is $\beta=0.3$.

\paragraph{Training setup.}
The released training configuration optimises the model end to end for $150$ epochs using AdamW with learning rate $1\times10^{-3}$, weight decay $1\times10^{-3}$, batch size $128$, and validation after every epoch. The data pipeline applies random horizontal and vertical flips, random autocontrast ($p=0.05$), and random rotations up to $45^\circ$ on the resized ROI tensors. The CAH loss introduces an additional linear classifier and centroid bank during training, but inference uses only the $256$-dimensional embeddings extracted by the DscGrapher encoder, which are compared by cosine similarity for verification. The inference network itself contains approximately $4.76$ million trainable parameters.

\paragraph{Latency and computational cost.}
Using the same benchmarking protocol as in Point~12, namely batch size $1$ with $20$ warm-up and $200$ timed forward passes, the proposed model requires approximately $5.07$ GFLOPs per $224\times224$ image. On the held-out FV-300 checkpoint, the mean forward-pass latency is $55.82$ ms on CPU and $13.00$ ms on an NVIDIA L40S GPU, corresponding to $17.92$ and $76.94$ images/s respectively. These measurements refer to the inference-time encoder forward pass, not the training-only loss heads. The resulting cost is higher than that of the lightest baselines, but it remains within a practical real-time GPU regime while delivering the strongest cross-dataset recognition performance among the learned methods evaluated in this work.

\section*{Baseline Training Details and Fairness}

\paragraph{Reviewer clarification addressed.}
We agree that the revised manuscript should state the baseline training setup more explicitly. The summary below is taken from the per-method configuration files together with the shared training drivers used in our codebase. In our experiments, the deep baselines were \emph{retrained by us} under the same leave-one-dataset-out protocol used for the proposed method; the reported deep-learning results were not copied directly from the original papers. ArcVein, LGFIN, FV-ViT, Chen et al., and the proposed model were trained in our PyTorch framework, while VeinAttNet was retrained separately in MATLAB using the published architecture implemented in our codebase. MCP, RLT, and WLD are handcrafted non-learning pipelines, so optimizer, learning rate, epochs, and loss settings are not applicable to them.

\paragraph{Shared protocol and augmentation policy.}
For fairness, all learned methods used the same source/target partitioning, the same four statistical seeds per leave-out dataset, and the same evaluation code for AUC/EER/TAR computation. For the PyTorch models, the input ROI was converted from grayscale to three channels and then processed by the shared leave-one-dataset-out wrapper with random horizontal and vertical flips, random autocontrast ($p=0.05$), random rotations up to $\pm 45^\circ$, and resizing to the method-specific input resolution. VeinAttNet used its own MATLAB augmentation pipeline with random horizontal reflection, random translations in both axes (up to $\pm 30$ pixels), random rotations up to $\pm 45^\circ$, random scaling in $[0.9, 1.1]$, and grayscale-to-RGB conversion. Importantly, we did not perform dataset-specific retuning on the held-out target set; for each learned method, a single training configuration was kept fixed across all leave-out experiments, except for the unavoidable change in the number of source classes.

The comparison is therefore fair in the sense that all learned methods were retrained and evaluated under the same cross-dataset protocol, with matched statistical seeds and a common metric pipeline, rather than mixing our own retrained models with numbers copied from different papers. At the same time, the comparison is not ``identical-hyperparameter'' across methods: each baseline retained its own architecture-specific input size, loss formulation, optimizer schedule, batch size, and learning rate. Forcing all methods to use exactly the same optimizer and resolution would itself introduce a different source of unfairness. The revised manuscript will make this distinction explicit.
